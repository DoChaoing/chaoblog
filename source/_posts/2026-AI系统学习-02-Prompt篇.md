Prompt 的目标不是写一句漂亮的话，而是把任务、上下文、约束和输出格式设计清楚，让模型稳定完成工作。

## Prompt 的基本结构

一个实用 Prompt 通常包含：

| 部分 | 说明 |
|:--|:--|
| 角色 | 让模型知道应该以什么身份处理问题 |
| 任务 | 明确要完成什么 |
| 上下文 | 提供必要背景和资料 |
| 约束 | 说明不能做什么、必须遵守什么 |
| 输出格式 | 要 Markdown、JSON、表格还是代码 |
| 示例 | 给模型一个可模仿的输入输出样例 |

空泛的 Prompt 往往会得到空泛的回答。好的 Prompt 应该能减少歧义。

## 结构化输出

真实应用里，模型输出经常要被程序继续处理，所以结构化输出非常重要。

例如：

```json
{
  "category": "技术问题",
  "priority": "high",
  "summary": "用户反馈登录失败",
  "confidence": 0.86
}
```

结构化输出要配合字段说明、示例和校验逻辑。不要只要求“输出 JSON”，还要说明字段含义、可选值和失败时怎么返回。

## 函数调用

函数调用让模型不只是生成文本，还能选择工具并提供参数。它适合：

- 查询数据库；
- 调用搜索；
- 计算数据；
- 创建任务；
- 读取业务资料。

工具定义要清楚，包括名称、描述、参数类型、必填字段和错误返回。

## 常见问题

| 问题 | 解决方式 |
|:--|:--|
| 输出格式不稳定 | 使用 JSON Schema、示例和校验 |
| 回答太发散 | 降低 temperature，收紧任务边界 |
| 字段缺失 | 明确必填字段和空值处理 |
| 工具参数错误 | 加参数校验和错误重试 |
| 结果不可复现 | 固定 Prompt 版本并记录日志 |

## 学习目标

这一篇要解决一个核心问题：如何把“和模型聊天”变成“让模型稳定完成任务”。

读完以后，你应该能做到：

- 写出有角色、任务、上下文、约束、输出格式的 Prompt；

- 判断什么时候该用函数调用；
- 通过测试样例迭代 Prompt。

## Prompt 从差到好的变化

差的 Prompt：

```text
帮我总结一下这段内容。
```

更好的 Prompt：

```text
你是一个技术文档编辑。请把下面内容总结成 5 条要点。
要求：
1. 每条不超过 30 字；
2. 保留关键技术名词；
3. 不要添加原文没有的信息；
4. 输出 Markdown 列表。

原文：
{{content}}
```

差别不在字数，而在任务边界是否清楚。

## Prompt 模板设计

可以沉淀一套通用模板：

```text
角色：
你是 {{role}}。

任务：
请完成 {{task}}。

输入：
{{input}}

约束：
- {{constraint_1}}
- {{constraint_2}}

输出格式：
{{format}}

如果信息不足：
请返回“不确定”，并说明缺少什么信息。
```

这类模板适合放进项目代码里，配合版本号管理。

## 结构化输出设计原则

结构化输出不是字段越多越好，而是越稳定越好。

| 原则 | 说明 |
|:--|:--|
| 字段少而明确 | 先保证核心字段稳定 |
| 类型清晰 | 字符串、数字、数组、枚举要明确 |
| 可空规则 | 信息不存在时返回 null 还是空字符串 |
| 错误格式 | 模型无法判断时如何返回 |
| 示例驱动 | 给 1 到 3 个输入输出示例 |

示例：

```json
{
  "is_answerable": true,
  "answer": "根据文档，系统支持向量检索。",
  "sources": ["doc_01.md#section-2"],
  "confidence": 0.78
}
```

## 函数调用与普通 Prompt 的区别

普通 Prompt 适合生成文本；函数调用适合让模型决定“该调用哪个外部能力”。

| 场景 | 推荐方式 |
|:--|:--|
| 总结文章 | 普通 Prompt |
| 抽取字段 | 结构化输出 |
| 查询订单 | 函数调用 |
| 搜索知识库 | 函数调用 + RAG |
| 多步任务 | Agent |

函数调用不是万能的。工具描述不清楚、参数 Schema 太宽松、错误处理缺失，都会让调用结果不稳定。

## Prompt 评测方法

Prompt 迭代要靠样例集，不要靠感觉。

| 测试类型 | 示例 |
|:--|:--|
| 正常输入 | 信息完整，应该稳定输出 |
| 边界输入 | 字段缺失、文本很短、文本很长 |
| 干扰输入 | 包含无关内容或冲突信息 |
| 恶意输入 | 试图覆盖系统指令 |
| 不可回答 | 信息不足，应该拒答 |

每次改 Prompt 后，都用同一批样例跑一遍，记录格式错误率、字段缺失率和事实错误。

## 常见优化手段

- 降低 temperature，让结果更稳定；
- 增加 few-shot 示例；
- 把复杂任务拆成多个步骤；
- 使用 JSON Schema 校验；
- 输出前让模型自检；
- 对失败样例单独补充规则；
- 把 Prompt 版本写入日志。

## 实战任务

做一个“简历信息抽取器”：

1. 输入一段简历文本；
2. 抽取姓名、岗位、技能、项目、年限；
3. 输出 JSON；
4. 用 Schema 校验；
5. 对 20 条样例统计成功率；
6. 记录 5 个失败案例。

## 检查清单

- Prompt 是否有明确角色；
- 是否说明输入是什么；
- 是否明确不能编造；
- 是否指定输出格式；
- 是否有示例；
- 是否有无法判断时的返回规则；
- 是否有测试样例；
- 是否记录版本。

## 面试表达

> 我做 Prompt 时会把任务拆成角色、任务、上下文、约束和输出格式。对于需要进入程序处理的场景，我会要求 JSON 输出，并配合 Schema 校验。Prompt 迭代不是凭感觉，我会准备正常、边界、干扰和不可回答样例，每次改动都跑一遍，记录格式错误和字段缺失。
