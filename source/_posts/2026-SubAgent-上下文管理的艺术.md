Agent 工程的核心矛盾：模型能力随上下文丰富度上升，但上下文窗口有限、越来越贵、塞满了还会让注意力稀释。子代理（Sub Agent）是主要解法之一——**让它自己的窗口去承受过程，主对话只接收结论**。

## 模式

```text
主对话（宝贵，保持干净）
  ├─ 委派："搜一下项目里所有处理支付回调的代码，总结入口和校验逻辑"
  │     └─ 子代理在独立上下文里翻几十个文件 → 返回 300 字结论
  ├─ 主对话拿到结论继续决策
  └─ 中间翻过的 50 个文件内容，从未进入主上下文
```

子代理是一个独立上下文的 Agent，有自己的系统提示、自己的工具循环、自己的历史记录。它不知道主对话聊了什么——这正是它的价值，也是它的限制。

## 内置能力与自定义

Claude Code 自带几种委派方式：

- **Explore / general-purpose**：内置的探索型和通用型子代理，前者擅长大规模只读搜索，后者可以多步骤执行；
- **Fork**：从当前对话分叉出一个继承完整上下文的代理，适合"验证一个想法但不想污染主线"的支线任务。

更常见的是定义专属子代理，`.claude/agents/code-reviewer.md`：

```markdown
---
name: code-reviewer
description: 审查代码改动，在提交或 PR 前使用。重点看正确性、边界条件和测试覆盖。
tools: Read, Grep, Glob, Bash
model: inherit
---

你是资深代码审查者。审查时：

1. 先看改动范围（git diff），再看改动涉及的上下游代码
2. 每个发现必须给出：问题描述、触发场景、建议修法
3. 不确定的风格问题标注为"建议"，正确性问题标注为"必须修复"
```

frontmatter 里 `tools` 限制它能用的工具（审查器不需要写文件），`description` 决定主模型什么时候自动委派给它——和 Skill 的 description 一样，写清楚触发时机。

## 什么时候委派

适合委派的任务有共同特征：

- **产生大量中间输出**：全库搜索、读长日志、批量分析文件——垃圾留在子代理窗口里；
- **边界清晰、可独立验证**：能写成"输入是什么、输出长什么样"的任务；
- **可并行**：同时审查三个模块、同时调研三个技术方案，互不依赖的任务可以并发派发。

不适合委派的：需要主对话连贯意图的决策（架构选择）、强依赖前文讨论上下文的任务（子代理看不到主对话历史）、一问一答的小事（委派本身有开销，不如直接答）。

## 代价

子代理不是免费的：

- 每个子代理都从头加载自己的系统提示和工具定义；
- 它看不到主对话，任务描述必须自包含——写不清就返工；
- 返回结论的质量取决于你对"输出长什么样"的约束，不约束就给你写一篇散文。

经验：委派前先问一句"这个任务的中间过程，主对话需要看吗？"——不需要，就委派。
