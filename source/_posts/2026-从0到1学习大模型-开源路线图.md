大模型学习最常见的误区，是把四种完全不同的事塞进同一个待办：调 API、微调模型、从头训练、部署推理服务。它们共享一些词汇，却需要不同的数学、工程和算力。

如果目标不分开，学习很容易变成一种熟悉感：看过 Transformer 图、跑过聊天框、装过 Agent 框架，但没有任何一个系统真正从输入跑到可验证的输出。

这篇路线只推荐能交付东西的学习材料。每一段都有一个开源项目、一个完成标准和一个明确的止损点。

## 先选你要学会的那件事

| 目标 | 真正需要理解的部分 | 暂时不要做 |
|:--|:--|:--|
| 做 AI 应用 | 模型调用、结构化输出、检索、评测、权限 | 自己预训练一个模型 |
| 理解模型内部 | tokenizer、attention、反向传播、训练循环 | 一开始追最新 70B 模型 |
| 做模型训练/后训练 | 数据、SFT、偏好优化、评测、分布式训练 | 把一次 loss 下降当成效果证明 |
| 做推理平台 | 显存、KV cache、批处理、量化、压测 | 先写多 Agent 编排 |

大多数开发者应该走第一列，再选第二列补基础。训练一遍小 GPT 的价值是理解训练链路，而不是得到一个能与商业模型竞争的助手。

## 项目一：用 Python 写出一个小 GPT，理解“模型到底在算什么”

推荐从 [Sebastian Raschka 的 LLMs-from-scratch](https://github.com/rasbt/LLMs-from-scratch) 开始。它按 tokenizer、embedding、attention、GPT 架构、预训练与微调的顺序提供可运行代码，适合有 Python 和 PyTorch 基础的人。

本阶段不要追求完整复刻。只做三件事：

1. 让 tokenizer 把文本变成 token，再把 token 还原；
2. 实现并打印一个 causal attention 的张量形状；
3. 在很小的数据上训练到 loss 确实下降，并保存一次 checkpoint。

完成标准不是“模型会写诗”，而是你能解释：为什么预测下一个 token；为什么注意力不能看未来；为什么训练和生成使用同一组权重却有不同的计算方式。

如果你连 PyTorch 张量都不熟，先看 [Hugging Face LLM Course](https://huggingface.co/learn) 的基础单元。它的价值不在于记住某个 API，而在于建立 token、Transformer、训练与推理之间的共同语言。

## 项目二：从训练数据到评测，完成一次小模型训练闭环

当“小 GPT”不再神秘后，再进入 [Stanford CS336：Language Modeling from Scratch](https://cs336.stanford.edu/spring2025/index.html)。这门课把数据收集与清洗、Transformer 构建、训练和部署前评测放在同一条链路中；它比“手写 Transformer”更接近真实训练系统。

个人学习不需要复现它的全部作业。挑一个小数据集，维护以下四份东西就够了：

```text
data/      原始数据来源、许可和清洗脚本
configs/   模型大小、学习率、随机种子
runs/      loss、吞吐、显存和 checkpoint 元信息
eval/      固定提示词、预期性质、失败样例
```

最重要的产出是一页实验记录：改了什么、为什么改、loss/速度怎样变化、生成样本哪里变好或变坏。没有这页记录，训练只是一次昂贵的抽奖。

想看更靠近底层的实现，可以把 [Karpathy 的 llm.c](https://github.com/karpathy/llm.c) 当作进阶阅读。它用原始 C/CUDA 展示 GPT-2 训练，适合理解 kernel、内存和训练性能；但它需要 CUDA 环境，不是第一个项目。

## 项目三：把模型接进一个有边界的应用

到这里再做应用。选一个只有一个核心动词的需求，例如：

- 从会议纪要提取待确认事项；
- 根据已授权文档回答制度问题并给出处；
- 从票据图片生成字段草稿，用户确认后入账。

应用的第一版应只有一条链路：`输入 → 模型草稿 → Schema 校验 → 人工/规则确认 → 保存或展示`。模型不直接写数据库、不替用户发送邮件、不拥有数据库权限。

接下来才考虑 RAG。把它理解为证据检索，而不是“给模型加记忆”：资料必须有来源、版本和访问控制；答案必须能指出引用；资料不足时必须允许拒答。

[Full Stack Deep Learning 的 LLM Bootcamp](https://fullstackdeeplearning.com/llm-bootcamp/) 值得在这个阶段跟。它把模型能力、数据、产品与部署放在一起讨论；[Eugene Yan 的文章库](https://eugeneyan.com/writing/) 则适合反复查阅评测、RAG、缓存和用户反馈等生产问题。

完成标准：准备至少 20 条脱敏样本，其中包含正常、模糊、资料不足和越权四类。每次修改模型、提示词或检索后，都重跑这 20 条。

## 项目四：再学 Agent 与推理部署

Agent 不是路线起点，而是“模型需要根据中间结果选择下一步”时的工具。先用两个只读工具，例如查询订单和检索帮助文档；每次工具调用由服务端重新做权限校验；写操作必须转到用户确认。

[Hugging Face Agents Course](https://huggingface.co/learn/agents-course/unit0/introduction) 提供了工具、框架、Agentic RAG 和评测项目的完整路径。若想读一个实现很小的框架，可看 [smolagents](https://github.com/huggingface/smolagents)：它的核心代码量刻意很小，支持工具与 sandbox，是研究 Agent 循环的好材料。不要因为“多 Agent”听起来前沿就先搭多个角色；无法评测一个 Agent 时，多加几个只会扩大不确定性。

有 NVIDIA GPU、并且已经完成应用评测后，再试 [vLLM](https://github.com/vllm-project/vLLM)。它把服务端真正关心的问题暴露出来：KV cache、continuous batching、prefix caching、量化、吞吐和延迟。启动服务不等于完成部署；至少用自己的请求分布做一次压测，记录首 token 时间、生成速度、并发下错误率与显存。

## 当前值得跟踪的技术，不必立刻全学

下面这些方向正在改变工程决策，但它们不是新手的待办清单：

| 方向 | 它改变了什么 | 应在何时学习 |
|:--|:--|:--|
| 后训练与推理时扩展 | 模型效果越来越依赖数据、验证器和测试时计算，而非只看预训练参数量 | 已能训练并评测小模型后 |
| MoE 与长上下文 | 模型架构和内存/带宽约束变复杂 | 读模型论文或做服务优化时 |
| Agent + MCP | 外部工具与上下文的接入方式更标准化 | 已有明确工具、权限和审计需求时 |
| 高效推理 | 量化、KV cache、批处理直接影响单位成本与延迟 | 准备自部署或有稳定流量时 |
| 多模态 | 输入从文本扩展到图片、音频、视频 | 业务输入确实需要这些模态时 |

“最新”不等于“现在该学”。判断一项技术是否值得投入的标准是：它是否解决了你正在运行的系统的瓶颈，且你能设计指标验证收益。

## 一个八周的最小节奏

| 周 | 只做一件事 | 留下的证据 |
|:--|:--|:--|
| 1 | 完成 tokenizer 与 attention 小实验 | notebook + 张量解释 |
| 2 | 训练一个小 GPT | config、曲线、checkpoint |
| 3 | 清洗数据并写固定评测 | 数据卡 + 20 条评测样本 |
| 4 | 做一次 SFT 或分类微调 | 前后对比与失败样例 |
| 5 | 做一个结构化输出的小应用 | API、Schema、人工确认流 |
| 6 | 加检索与引用 | 文档元数据、命中记录、拒答题 |
| 7 | 加两个受限工具或 Agent | trace、权限拒绝与超时测试 |
| 8 | 部署或压测 | 延迟、成本、错误率和 README |

八周后你不会“学完大模型”，但会拥有一条完整的证据链：理解过模型、训练过小实验、做过可用功能、测过错误，也知道自己下一步该去模型、数据还是系统层解决问题。

- [LLMs-from-scratch](https://github.com/rasbt/LLMs-from-scratch)：最适合从 PyTorch 建立模型直觉的代码仓库。

- [llm.c](https://github.com/karpathy/llm.c)：面向 C/CUDA 的训练实现进阶材料。

- [Hugging Face Agents Course](https://huggingface.co/learn/agents-course/unit0/introduction)：从 Agent 基础到评测项目的实践课程。
- [vLLM](https://github.com/vllm-project/vLLM)：开源推理与服务系统的主线项目。
