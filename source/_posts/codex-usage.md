## 前言

这篇文章记录我在实际项目里使用 Codex 的方法与经验，目标是**让需求更快落地、减少上下文切换、降低沟通成本**。如果你也在写代码、维护文档或做重复性的工程任务，希望这份笔记能给你一些可直接复用的操作套路。

## 我用 Codex 解决哪些问题

- **小而明确的变更**：快速定位、编辑、验证、提交。
- **中等规模改动**：把任务拆成可执行步骤，逐步完成并保持可回滚。
- **内容产出**：生成技术说明、变更说明、以及博客初稿。
- **维护性工作**：整理目录、重构配置、批量替换、补齐测试。

## 最小可用工作流（推荐）

1. **明确目标**：一句话描述结果，比如“新增一篇 Codex 使用的博客并部署”。
2. **快速扫描**：让 Codex 列出相关文件、依赖与入口。
3. **小步提交**：每次只做一个子任务，确保可验证。
4. **本地验证**：能跑就跑，能看就看。
5. **总结与下一步**：让输出更易复用。

## 提示词（Prompts）模板

以下是我常用的提示方式，结构化输入会明显提升输出质量：

```
目标：
- 想完成的结果

约束：
- 不能改哪些文件
- 要使用哪些工具/命令

输出：
- 需要哪些文件改动
- 需要什么验证步骤
```

如果涉及多步骤任务，可以在“约束”里强调“先给出计划，再执行”，这样更稳。

## 和 Hexo 配合的实践

在 Hexo 项目里，我通常用 Codex 做这些事：

- 生成 Markdown 博文初稿并统一格式
- 自动补齐 Front Matter
- 修改主题或配置时，先定位再改动
- 生成部署说明或变更日志

## 常见注意事项

- **提需求尽量具体**：模糊需求会导致偏题或过度推断。
- **小步快跑**：先让 Codex 做最小可行变更，再逐步增强。
- **保留可验证的证据**：让它输出执行的命令和改动文件。
- **不要跳过本地验证**：尤其是涉及构建与部署。

## 结语

Codex 更像一个“执行力很强的同伴”，而不是一键完成所有问题的工具。把任务拆小、明确目标、快速验证，才是最稳的用法。
