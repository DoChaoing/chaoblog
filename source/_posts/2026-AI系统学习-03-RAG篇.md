做 RAG 时最令人困惑的一句话是：

> 文档明明上传了，为什么它还是答错？

这句话里至少藏着五种问题：文档有没有被解析、关键段有没有被切开、查询有没有召回它、召回结果有没有塞进 Prompt、模型有没有严格依据证据回答。

所以 RAG 不是“把 PDF 丢进向量数据库”。它是一条从原始资料到最终答案的**证据链**。任何一环断掉，用户看到的都是“AI 不靠谱”。

## 用一个故障建立排查思路

假设制度文档写着：

```text
远程办公申请：每月最多 8 天；跨城市远程办公须提前 5 个工作日提交审批。
```

用户问：“去外地远程办公需要提前多久申请？”系统回答“提前 3 天”。

不要马上改 Prompt。先按这个顺序查：

```text
原始文档
  -> 解析出的纯文本
  -> 分块后的 chunk 与 metadata
  -> 本次查询的 top-k 结果
  -> 实际送入模型的 context
  -> 最终回答与引用
```

只有看到每一层的实际数据，才能判断“3 天”从哪里来的。可能是旧版本文档被召回了，也可能关键句被截成了两块，甚至模型根本没拿到任何资料。

## 先定义一个可追溯的数据结构

不要只存一段字符串和一个向量。每个 chunk 至少带上来源：

```python
from dataclasses import dataclass

@dataclass
class Chunk:
    id: str
    content: str
    source: str          # remote-work-policy.md
    version: str         # 2026-01
    section: str         # 跨城市远程办公
    page: int | None
    updated_at: str
```

这些 metadata 有三个用途：

- 返回给用户，让回答可以点击或定位来源；
- 检索时过滤过期版本、错误权限或错误业务线；
- 排错时知道错误答案来自哪个文件、哪个段落。

没有来源的 RAG 回答，本质上仍然是“请相信模型”。

## 分块的目标是保留能回答问题的最小证据

固定按 500 字符切块很容易实现，但经常破坏语义：标题在上一块，规则和例外在下一块；表格被打散；“不得”留在前一块，条件留在后一块。

一个更稳妥的起点是：

1. 按文档标题或语义段落切；
2. 过长的段落再按句子或 Token 上限拆；
3. 保留少量 overlap，让条件和例外不要分家；
4. 把标题拼到 chunk 前面；
5. 为每块记录版本、页码、章节和权限。

例如：

```text
[远程办公制度 > 跨城市远程办公]
跨城市远程办公须提前 5 个工作日提交审批。
每月最多 8 天，特殊情况需部门负责人批准。
```

这比孤零零的一句“须提前 5 个工作日提交审批”更利于检索和生成。

## 检索不是只有 top-k

向量检索解决“语义相近”，关键词检索解决“精确术语”。真实资料里常同时需要两者：用户可能问“远程”，文档写“异地办公”；也可能问政策编号、产品名、金额，这些精确词不应被语义相似度稀释。

一个够用的检索策略可以是：

```text
query 规范化
  -> 向量召回 + 关键词召回
  -> 合并去重
  -> metadata 过滤（权限、版本、业务范围）
  -> rerank
  -> 取少量高质量 chunk 进入生成
```

不要一开始追求最复杂的混合检索。先把每一步的候选结果记录下来，用评测集证明它确实提升了召回。否则你只是在给系统增加无法解释的复杂度。

## 生成层必须知道“证据不足”

下面的 Prompt 比“请根据资料回答”更可用：

```text
你是制度问答助手。只能依据 <context> 中的资料回答。
若资料不能直接支持结论，回答“当前资料无法确认”，不要使用外部常识补全。
回答时给出 source_id；不要引用未提供的来源。

<context>
[chunk: policy-2026-01-remote-03]
远程办公制度 > 跨城市远程办公：须提前 5 个工作日提交审批。
</context>
```

生成结果应包含答案和引用，而不是只给自然语言：

```json
{
  "answer": "跨城市远程办公须提前 5 个工作日提交审批。",
  "source_ids": ["policy-2026-01-remote-03"],
  "grounded": true
}
```

程序仍应校验 `source_ids` 是否确实属于本次召回结果。模型不能自行创造引用编号。

## 评测时，把“答错”拆成不同指标

只看最终答案对不对，很难知道该改分块还是改 Prompt。建议维护一个小型评测集：

| 问题 | 期望 chunk | 期望结论 | 允许拒答 |
|:--|:--|:--|:--:|
| 去外地远程需提前多久？ | remote-03 | 5 个工作日 | 否 |
| 每月可远程几天？ | remote-02 | 最多 8 天 | 否 |
| 可否报销远程办公设备？ | 无 | 无法确认 | 是 |

至少观察四件事：

- **召回率**：期望 chunk 是否进入候选；
- **排序质量**：期望 chunk 是否排在靠前位置；
- **引用正确率**：回答是否引用了真正支持它的 chunk；
- **拒答正确率**：无资料时是否没有编造。

如果期望 chunk 根本没进 top-k，应查解析、分块或召回；如果进了但模型没用，应查 context 组织与 Prompt；如果答案对却引用错，系统仍不可信。

## RAG 最常见的四个坑

| 坑 | 表现 | 修复方向 |
|:--|:--|:--|
| 只看最终回答 | 不知道错误发生在哪一层 | 保存 chunk、候选、context 和引用 |
| 文档更新不重建索引 | 旧制度与新制度混答 | 版本化、增量索引、过期数据下线 |
| 把 top-k 调得很大 | 噪声增加，模型更容易混淆 | 先看 rerank 与证据质量 |
| 只做“有答案”的题 | 系统会在未知问题上乱答 | 加入应拒答、冲突资料和权限题 |

## 本篇练习：让一次答案可以被追责

拿三篇短 Markdown 文档做一个最小知识库。要求不是页面好看，而是每次回答都能回答下面五个问题：

1. 原始答案来自哪篇文档、哪一段？
2. 该段为什么会被召回？它排第几？
3. 本轮实际送给模型的 context 是什么？
4. 模型引用的来源是否真的支持结论？
5. 没有资料时是否稳定拒答？

把这五项写进日志和评测表。等它们都能回答清楚，再去尝试 query rewrite、hybrid search 或 rerank。下一篇我们再讨论：当系统不仅要回答，还要选择并调用工具时，如何避免它失控循环。
