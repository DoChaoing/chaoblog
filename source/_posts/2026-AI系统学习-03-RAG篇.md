RAG 的核心是把外部知识接入模型：先从知识库检索相关内容，再让模型基于这些内容回答。它常用于企业知识库、客服问答、文档助手和内部搜索。

## RAG 基本链路

```text
文档
  -> 解析清洗
  -> 分块
  -> Embedding
  -> 向量数据库
  -> 用户提问
  -> 检索相关片段
  -> 组装上下文
  -> 模型回答
  -> 返回引用来源
```

RAG 不是把文件丢给模型这么简单。真正影响效果的是文档质量、分块策略、检索召回、重排和评测。

## Embedding 与向量数据库

Embedding 会把文本转成向量，让语义相近的内容在向量空间里更接近。向量数据库负责存储和检索这些向量。

常见选择：

| 方案 | 适合场景 |
|:--|:--|
| FAISS | 本地实验，速度快 |
| Chroma | 学习和小型项目 |
| pgvector | 已经使用 PostgreSQL 的项目 |
| Milvus | 更大规模向量检索 |

学习阶段不必纠结工具，先把链路跑通。

## 检索优化

常见优化方向：

- 调整 chunk size 和 overlap；
- 保留标题层级和元数据；
- 使用关键词检索 + 向量检索；
- 对召回结果做 rerank；
- 对用户问题做 query rewrite；
- 回答时展示引用来源。

如果 RAG 答错，要先判断是文档解析、分块、召回、重排还是生成出了问题。

## 评测问题

至少准备 30 条问题：

- 能直接从资料回答的问题；
- 需要跨段落整合的问题；
- 资料中没有答案的问题；
- 容易混淆的边界问题。

每条问题记录标准答案、实际答案、引用来源和错误类型。

## 本篇练习

做一个最小 RAG 知识库：

1. 读取 Markdown 或 PDF；
2. 分块并生成 Embedding；
3. 写入向量库；
4. 输入问题后检索相关片段；
5. 基于片段回答；
6. 展示引用来源；
7. 记录 bad case。

## 学习目标

RAG 篇要让你掌握一件事：如何让模型基于外部资料回答，而不是凭模型记忆猜。

你应该能做到：

- 解释 RAG 的完整链路；
- 设计文档分块策略；
- 使用 Embedding 和向量数据库；
- 理解召回、重排和引用来源；
- 用评测集判断 RAG 是否有效；
- 分析一个 RAG bad case 来自哪一层。

## 文档处理

RAG 的效果从文档处理开始。文档质量差，后面模型再强也很难救。

常见文档类型：

| 类型 | 处理重点 |
|:--|:--|
| Markdown | 保留标题层级和段落结构 |
| PDF | 注意页眉页脚、表格、换行错误 |
| Word | 注意列表、标题、表格 |
| 网页 | 去掉导航、广告、无关内容 |
| 表格 | 转成结构化文本或独立字段 |

清洗时要保留元数据，比如文件名、章节标题、页码、更新时间。这些信息后面可以用于引用来源。

## 分块策略

分块是 RAG 的核心技术点之一。

| 策略 | 优点 | 缺点 |
|:--|:--|:--|
| 固定长度分块 | 简单，容易实现 | 容易切断语义 |
| 按标题分块 | 保留结构 | 章节过长时仍需二次切分 |
| 语义分块 | 更符合内容边界 | 实现复杂 |
| 滑动窗口 | 保留上下文 | 存储和检索成本更高 |

学习阶段可以从“标题 + 固定长度 + overlap”开始。比如每块 500 到 800 中文字，overlap 100 到 150 字，再根据评测结果调整。

## 检索流程

一次检索通常包括：

```text
用户问题
  -> query 改写
  -> 向量检索 top-k
  -> 可选关键词检索
  -> 合并结果
  -> rerank
  -> 组装上下文
```

如果问题很短，可以做 query rewrite，把用户问题改写成更适合检索的版本。如果资料很多，可以加入重排模型，把最相关的片段排到前面。

## 生成阶段 Prompt

RAG 的生成 Prompt 要特别强调依据来源。

示例结构：

```text
你是知识库问答助手。请只根据给定资料回答问题。
如果资料中没有答案，请回答“资料中没有找到明确答案”。
回答必须包含引用来源。

用户问题：
{{question}}

资料片段：
{{contexts}}

输出格式：
答案：
引用：
```

这能减少模型脱离资料自由发挥。

## RAG 常见错误定位

| 现象 | 可能原因 | 排查方式 |
|:--|:--|:--|
| 回答完全不相关 | 检索召回错了 | 查看 top-k 片段 |
| 回答缺少关键点 | 分块太碎或 top-k 太小 | 检查标准答案在哪些片段 |
| 回答编造 | 生成 Prompt 约束不够 | 要求只基于资料并引用 |
| 引用不准确 | 来源元数据丢失 | 检查文档解析和 chunk metadata |
| 问不到表格内容 | 表格解析差 | 把表格转成结构化文本 |

RAG 调试时不要只看最终答案，要看检索片段。

## 评测表模板

建议建立一个表：

| 问题 | 标准答案 | 期望来源 | 实际答案 | 实际来源 | 错误类型 | 修复方案 |
|:--|:--|:--|:--|:--|:--|:--|
| 示例问题 | 标准答案 | doc.md | 模型答案 | doc.md | 召回错误 | 调整分块 |

错误类型可以分为：解析错误、分块错误、召回错误、重排错误、生成错误、资料缺失。

## 进阶优化路线

1. 基础向量检索；
2. 加 metadata 过滤；
3. 加关键词检索；
4. 加 rerank；
5. 加 query rewrite；
6. 加引用校验；
7. 加 bad case 回归测试；
8. 加多轮问答上下文压缩。

每次只加一个优化点，否则你很难判断效果来自哪里。

## 面试表达

> 我的 RAG 项目会拆成文档解析、分块、Embedding、向量检索、重排、生成和评测几层。答错时我不会只改 Prompt，而是先看检索结果。如果 top-k 片段没有召回标准答案，就是检索问题；如果片段正确但回答错，就是生成约束或上下文组织问题。项目里我会记录问题、标准答案、召回片段和错误类型，持续优化。
