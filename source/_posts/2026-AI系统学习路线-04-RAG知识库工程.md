> **一句话**：RAG 不是“向量库 + 大模型”，而是一条从文档到可信答案的工程链路。

<!-- more -->

## 1. RAG 解决什么

RAG 主要解决三件事：

| 问题 | RAG 怎么解决 |
|:--|:--|
| 模型不知道私有知识 | 从企业文档中检索 |
| 模型知识过期 | 接入实时或准实时数据 |
| 模型回答没依据 | 返回引用和证据 |

但 RAG 不负责让模型“变聪明”。它提供事实材料，模型负责理解和表达。

## 2. 标准链路

```text
文档上传
  -> 解析
  -> 清洗
  -> 分块
  -> Embedding
  -> 索引
  -> 查询改写
  -> 检索
  -> 重排
  -> 上下文压缩
  -> 生成答案
  -> 引用与评测
```

每一步都有坑。

## 3. 文档处理是 RAG 的地基

很多 RAG 效果差，不是向量库选错，而是文档处理差。

| 环节 | 常见问题 | 优化方向 |
|:--|:--|:--|
| 解析 | PDF 表格丢失、标题层级乱 | 保留结构，做格式识别 |
| 清洗 | 页眉页脚噪声多 | 去重、去模板文本 |
| 分块 | 固定长度切断语义 | 按标题、段落、语义切分 |
| 元数据 | 权限、来源、时间缺失 | 写入 doc_id、tenant_id、version |

## 4. 检索不是只有向量

| 检索方式 | 优点 | 缺点 |
|:--|:--|:--|
| 向量检索 | 语义召回好 | 精确词、数字、代码不稳定 |
| BM25 | 关键词强 | 同义词和语义弱 |
| 混合检索 | 兼顾语义和关键词 | 参数需要调 |
| Rerank | 提升排序质量 | 增加延迟和成本 |
| GraphRAG | 适合多跳关系 | 建图和维护成本高 |

生产系统一般从 baseline 开始：

```text
BM25 + Vector -> RRF 融合 -> Rerank -> TopK 上下文
```

## 5. RAG 评测

不要只看“感觉回答不错”。至少要评估：

| 指标 | 看什么 |
|:--|:--|
| Recall@K | 正确片段有没有被召回 |
| Precision@K | 召回结果噪声多不多 |
| Faithfulness | 答案是否忠于上下文 |
| Answer Relevance | 是否回答了问题 |
| Citation Accuracy | 引用是否对应答案 |

最有效的办法是维护一批 bad case。

## 6. 面试表达模板

可以这样讲一个 RAG 项目：

> 我先搭了一个 baseline：文档解析、语义分块、Embedding、向量检索和基于上下文生成。之后发现精确词和表格问题召回差，于是加入 BM25 混合检索、RRF 融合和 reranker。最后用 Recall@5、faithfulness 和人工 bad case 做回归，保证每次改 Prompt、分块和模型后效果可比较。

## 7. 本章产出

做一个最小但完整的 RAG：

- 支持上传 Markdown/PDF；
- 支持分块和 Embedding；
- 支持向量检索 + BM25；
- 回答时带引用；
- 有 20 条评测问题。
