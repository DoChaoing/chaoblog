项目实战的目标不是堆功能，而是把 AI 基础、Prompt、RAG、Agent 和工程化串成一个能展示的作品。

## 项目一：RAG 知识库

最小功能：

1. 上传或读取文档；
2. 文档分块；
3. 生成 Embedding；
4. 向量检索；
5. 模型回答；
6. 展示引用来源；
7. 记录评测结果。

进阶功能：

- 混合检索；
- 重排；
- query rewrite；
- 多轮问答；
- 资料不足时拒答。

## 项目二：工具调用 Agent

最小功能：

1. 接收用户目标；
2. 选择工具；
3. 调用工具；
4. 观察结果；
5. 输出最终答案；
6. 记录 trace。

推荐工具：

- 文档搜索；
- 计算器；
- 待办计划生成；
- 文件摘要；
- 数据查询。

## 项目三：AI 助手

把 RAG 和 Agent 合并成一个 AI 助手：

```text
用户问题
  -> 判断是否需要检索
  -> 判断是否需要工具
  -> 生成答案
  -> 返回引用和执行过程
```

这个项目适合放进作品集，因为它能体现完整 AI 应用能力。

## README 模板

项目 README 至少包含：

- 项目背景；
- 功能列表；
- 技术架构；
- 启动方式；
- 环境变量；
- 运行截图；
- 评测结果；
- bad case；
- 后续优化。

## 本篇练习

选择一个主项目完成到可展示状态。不要追求复杂，先保证别人能看懂、能运行、能追问。

## 学习目标

项目实战篇的目标是把前面 5 篇串起来，形成能写进简历的作品。

你最终至少要有一个主项目：

```text
AI 知识库助手
  = RAG 知识库
  + Prompt 结构化输出
  + Agent 工具调用
  + 评测和日志
  + README 和架构图
```

## 项目路线图

建议按版本迭代，不要一口气做大。

| 版本 | 功能 | 验收标准 |
|:--|:--|:--|
| V0 | 模型调用 | 能输入问题并返回答案 |
| V1 | Prompt 模板 | 能稳定输出 Markdown 或 JSON |
| V2 | 文档检索 | 能基于本地文档回答 |
| V3 | 引用来源 | 答案能显示来源 |
| V4 | 评测集 | 有 30 条问题和结果记录 |
| V5 | 工具调用 | 能调用搜索、计算或保存工具 |
| V6 | 工程化 | 有日志、错误处理、部署说明 |
| V7 | 作品集 | 有 README、截图、架构图、复盘 |

每个版本都能独立展示，避免做一半时完全不可用。

## README 应该怎么写

README 至少包含：

| 部分 | 内容 |
|:--|:--|
| 项目背景 | 解决什么问题 |
| 功能列表 | 支持哪些能力 |
| 技术架构 | 模块和数据流 |
| 快速开始 | 安装、配置、启动 |
| 环境变量 | 模型 Key、数据库配置 |
| 示例效果 | 截图或输出样例 |
| 评测结果 | 问题数量、错误类型、优化记录 |
| 后续计划 | 可继续优化的点 |

README 是面试官判断项目质量的第一入口。

## 最小技术栈

| 层 | 推荐 |
|:--|:--|
| 后端 | Python + FastAPI |
| 文档处理 | Markdown / PDF loader |
| 向量库 | Chroma 或 FAISS |
| 数据 | SQLite / JSON |
| 前端 | 简单 HTML 或 React |
| 部署 | Docker + 云服务器或平台服务 |
| 评测 | CSV + 脚本 |

学习阶段优先选择简单技术栈，减少无关复杂度。

## 项目复盘模板

每次迭代写复盘：

| 项目 | 内容 |
|:--|:--|
| 本次目标 | 要解决什么问题 |
| 实现方案 | 做了哪些模块 |
| 遇到问题 | 出现哪些错误 |
| 定位方式 | 怎么判断问题来源 |
| 解决方案 | 怎么修复 |
| 后续优化 | 还可以怎么改 |

这份复盘会直接变成面试回答。

## 面试表达

> 我的项目从最小模型调用开始，逐步加入 Prompt 模板、RAG 检索、引用来源、Agent 工具调用和评测日志。这样做的好处是每一步都能验证效果。遇到回答错误时，我会通过日志查看 Prompt、检索片段和模型输出，判断问题来自哪一层。
