很多 AI 项目停在“聊天框能回答”的阶段。它不一定没价值，但经不起三个问题：资料从哪来？回答错了怎么办？别人如何在自己的机器上复现？

一个适合作品集的项目，不需要功能很多；它需要有清楚的问题、可运行的闭环和能讲明白的取舍。这篇以“团队制度知识库助手”为例，把前面六篇内容收束成一个可以真正完成的项目。

## 先把项目缩小到一个可验收的问题

不要写“做一个通用 AI 助手”。从下面这种具体目标开始：

```text
已登录员工可查询自己有权限的制度 Markdown 文档。
系统返回基于文档的答案和引用来源；资料不足时拒答。
管理员可以查看评测结果与错误日志。
```

这个范围足够小，却已经覆盖了文档解析、RAG、Prompt、权限、评测、日志和部署。它比“接 20 个工具的超级 Agent”更容易完成，也更容易证明价值。

## 用版本，而不是功能清单，推动项目

每个版本都必须可运行、可演示、可验收：

| 版本 | 只解决一件事 | 验收方式 |
|:--|:--|:--|
| V0 | 能调用模型 | 输入问题，返回文本 |
| V1 | 输出可解析 | JSON Schema 校验通过 |
| V2 | 能检索本地文档 | 正确 chunk 出现在日志 |
| V3 | 答案可引用 | 页面显示文档名与段落 |
| V4 | 无资料会拒答 | 拒答题全部通过 |
| V5 | 可回归评测 | 一条命令跑完固定题 |
| V6 | 可观测与可部署 | 有日志、超时、README、Docker |

每完成一个版本就提交一次代码，并在 README 记录“新增了什么、用什么题验证、还有什么限制”。项目自然会形成一条可信的成长轨迹。

## 最小架构：先让数据流清楚

不需要一开始上微服务。一个清晰的单体结构就足够：

```text
Web UI
  -> API（鉴权、限流、request_id）
    -> Retriever（解析、分块、召回、rerank）
    -> Answer Service（Prompt、结构化输出、引用校验）
    -> Vector Store / 文档目录
    -> Logs + Evals
```

用户问问题时的数据流：

```text
用户问题
  -> 判断用户权限
  -> 召回其可见文档的相关 chunk
  -> 将少量 chunk 送入模型
  -> 校验 answer 与 source_ids
  -> 返回答案、引用、request_id
```

只要你能解释每个箭头的输入、输出和失败路径，这张图就比复杂的框图更有说服力。

## 一个适合维护的目录

```text
ai-policy-assistant/
  README.md
  .env.example
  docker-compose.yml
  app/
    api/          # 路由、鉴权、请求模型
    rag/          # loader、chunker、retriever
    prompts/      # 带版本的 Prompt
    services/     # 模型调用、回答校验
    observability/# 日志、指标、trace
  data/
    policies/     # 示例制度文档，禁止放敏感生产数据
  evals/
    cases.jsonl   # 问题、期望来源、期望答案/拒答
    run.py
  tests/
  docs/
    architecture.md
    bad-cases.md
  screenshots/
```

目录不是评分标准，但它应该让第一次打开仓库的人知道：如何启动、数据在哪、评测怎么跑、失败案例在哪。

## 别把“能答对”当作唯一效果

为项目准备 30 条左右小而真实的评测题，至少覆盖：

- 有明确答案的事实题；
- 需要引用正确章节的问题；
- 没有资料、应该拒答的问题；
- 文档版本冲突的问题；
- 无权限、应该拒绝的问题；
- 长问题、短问题和关键词不一致的问题。

每次演示时，主动展示一条成功题和一条拒答题。后者能说明你理解了边界，比只展示“模型好聪明”更可信。

## 设计一个真正有价值的 bad case

不要把 bad case 写成“模型偶尔回答不好”。下面这种记录才可复盘：

```text
现象：用户问“跨城市远程办公需提前多久”，系统答“3 天”。
定位：日志显示召回了 2025-09 旧制度，最新版本 metadata 未过滤。
修复：检索增加 effective_date 过滤；回答展示版本号。
验证：12 条版本题全部引用最新制度；旧版本题被拒答或标注历史版本。
代价：需要在文档入库时维护版本字段。
```

这段内容可以直接放进 README、项目复盘和面试讲稿，因为它包含问题、证据、方案、结果和取舍。

## README 是项目的第一个产品界面

一份好的 README 至少回答这些问题：

1. 项目解决谁的什么问题？
2. 最小功能与明确不支持的能力是什么？
3. 架构、数据流和技术选型是什么？
4. 本地启动需要哪些环境变量？
5. 如何导入示例数据、如何运行评测？
6. 有哪些截图、评测结果和已知限制？
7. 最值得讲的两个 bad case 是什么？

不要把 API Key、真实员工制度或生产日志放进仓库。用 `.env.example` 和脱敏的示例数据让别人可复现即可。

## 作品集完成定义

在继续加多模态、多 Agent 或花哨 UI 前，先检查：

- 新同学能在 15 分钟内启动项目；
- 每个答案能展示来源，且来源可定位；
- 评测脚本能运行，结果有记录；
- 至少有 3 个已修复 bad case；
- 系统遇到无资料、超时、无权限时不会伪装成成功；
- 你能在 3 分钟内讲清一条请求如何流过系统。

满足这些，项目已经足以体现 AI 应用工程能力。下一篇不再教你把项目包装得“很厉害”，而是教你如何只用真实证据，把它讲得可信、经得起追问。

完成知识库助手后，可以继续做 [AI 票据整理与消费复盘助手](/2026/08/04/2026-从0到1-AI票据整理与消费复盘助手/)。这个项目将票据图片转成需人工确认的结构化流水，再用数据库和只读工具完成消费查询，能补足视觉模型、数据校验与人机协作经验。
