Agent 的重点不是“模型更聪明”，而是让模型能够围绕目标选择工具、执行动作、观察结果，并决定下一步。

## Agent 基本循环

```text
目标
  -> 规划
  -> 选择工具
  -> 传入参数
  -> 执行工具
  -> 观察结果
  -> 继续或停止
```

这个循环必须有边界，否则很容易出现重复调用、工具参数错误、无法停止等问题。

## 工具调用

工具调用要关注：

| 要点 | 说明 |
|:--|:--|
| 工具描述 | 让模型知道什么时候该用这个工具 |
| 参数 Schema | 明确字段类型、必填项和可选值 |
| 参数校验 | 执行前检查输入是否合法 |
| 错误处理 | 工具失败时返回可理解错误 |
| 权限边界 | 危险操作必须限制或确认 |
| trace 日志 | 记录每一步，方便调试和复盘 |

## 记忆与状态

Agent 的记忆可以分成：

- 短期记忆：当前任务上下文；
- 长期记忆：用户偏好、历史结论、项目资料；
- 工具状态：已执行步骤和中间结果。

不要把所有历史都塞进上下文。更好的方式是筛选、总结和检索。

## MCP 是什么

MCP 可以理解为一种让模型接入外部工具和上下文的协议。它的价值在于把工具能力标准化，让 AI 应用更容易连接文件、数据库、浏览器、代码仓库等资源。

学习 MCP 时重点关注：

- 工具如何暴露；
- 参数如何定义；
- 权限如何控制；
- 调用结果如何返回给模型。

## 本篇练习

做一个小型 Agent：

1. 定义 `search_docs` 工具；
2. 定义 `calculate` 工具；
3. 让模型根据任务选择工具；
4. 设置最大轮数；
5. 记录每一步 trace；
6. 工具失败时返回错误并让模型恢复。

完成后，你应该能解释 Agent 为什么需要工具、状态、停止条件和日志。

## 学习目标

Agent 篇的目标是让你明白：Agent 不是一个神秘框架，而是一种“模型 + 工具 + 状态 + 控制循环”的系统设计。

学完后你应该能做到：

- 解释 Agent 和普通聊天机器人的区别；
- 定义一个工具的名称、描述和参数；
- 让模型根据任务选择工具；
- 控制 Agent 最大轮数和停止条件；
- 记录可复盘的 trace 日志；
- 说明 MCP 在工具接入中的价值。

## Agent 与工作流的区别

| 类型 | 特点 | 适合场景 |
|:--|:--|:--|
| 固定工作流 | 步骤固定，结果稳定 | 审批流、固定数据处理 |
| Agent | 步骤由模型动态决定 | 开放式任务、多工具探索 |
| 混合模式 | 主流程固定，局部由 Agent 决策 | 生产环境更常见 |

实际项目里不要为了 Agent 而 Agent。如果任务步骤明确，工作流更稳定；如果任务需要根据中间结果动态选择工具，才适合 Agent。

## 工具设计模板

一个工具至少要写清楚：

```json
{
  "name": "search_docs",
  "description": "在本地知识库中搜索和用户问题相关的文档片段",
  "parameters": {
    "query": "用户问题或检索关键词",
    "top_k": "返回结果数量，默认 5"
  }
}
```

工具描述要站在模型视角写，让模型知道什么时候使用它。参数越模糊，调用越容易错。

## Agent 执行 trace

每次执行都应该记录：

| 字段 | 说明 |
|:--|:--|
| task_id | 一次任务的唯一编号 |
| user_goal | 用户原始目标 |
| step | 当前第几步 |
| thought | 模型判断或计划 |
| tool_name | 调用的工具 |
| tool_args | 工具参数 |
| observation | 工具返回 |
| final_answer | 最终回答 |
| error | 错误信息 |

trace 是 Agent 调试和面试讲解最有价值的材料。没有 trace，Agent 出错时几乎无法复盘。

## 记忆设计

记忆不等于把所有历史塞给模型。

| 记忆类型 | 例子 | 存储方式 |
|:--|:--|:--|
| 会话记忆 | 当前对话目标和中间结果 | 当前上下文 |
| 长期记忆 | 用户偏好、项目背景 | 数据库或向量库 |
| 任务记忆 | 已调用工具、已完成步骤 | trace 状态 |
| 知识记忆 | 文档资料和历史问答 | RAG |

设计记忆时要考虑隐私、过期、冲突和召回策略。

## MCP 的理解方式

你可以把 MCP 理解成“模型连接外部能力的标准接口”。它解决的问题不是让模型变强，而是让工具接入更规范。

MCP 常见价值：

- 工具定义标准化；
- 上下文来源标准化；
- 更容易接入文件、数据库、浏览器、代码仓库；
- 更方便做权限控制；
- 不同客户端和工具之间更容易复用。

学习 MCP 时，不要只记协议名，要理解它解决的是工具接入和上下文接入的问题。

## 常见失败场景

| 失败场景 | 原因 | 解决方式 |
|:--|:--|:--|
| 工具一直重复调用 | 没有停止条件 | 设置最大轮数和完成判断 |
| 参数格式错误 | Schema 不清楚 | 强化参数描述和校验 |
| 调用了危险工具 | 权限边界缺失 | 加白名单和确认机制 |
| 工具失败后崩溃 | 没有错误恢复 | 统一错误返回格式 |
| 回答不看工具结果 | Prompt 没约束 | 要求基于 observation 回答 |

## 实战任务

做一个“资料检索 + 计划生成” Agent：

1. 用户输入学习目标；
2. Agent 调用 `search_docs` 查资料；
3. 调用 `make_plan` 生成学习计划；
4. 调用 `write_note` 保存结果；
5. 全程记录 trace；
6. 工具失败时返回可读错误。

## 检查清单

- 每个工具是否有清楚描述；
- 参数是否有类型和必填说明；
- 是否有最大轮数；
- 是否有停止条件；
- 是否记录 trace；
- 是否处理工具失败；
- 是否限制危险操作；
- 是否能解释每一步为什么调用工具。

## 面试表达

> 我理解 Agent 是模型驱动的工具调用循环。生产里最重要的不是让模型无限规划，而是控制工具定义、参数校验、最大轮数、错误恢复和 trace 日志。我会优先用固定工作流解决确定性任务，只在需要动态决策时引入 Agent。
