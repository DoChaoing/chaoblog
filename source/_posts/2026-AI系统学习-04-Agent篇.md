“让 Agent 自己完成任务”听起来很吸引人，直到你看到它在同一个搜索工具上调用了 12 次，花掉预算后仍没有答案。

这不是罕见边缘情况，而是 Agent 的默认风险：模型会根据当前观察选择下一步，但它并不天然理解你的成本上限、权限边界和“这件事已经失败三次”的含义。

因此，好的 Agent 不是更放任，而是**让每一次自主决策都被状态、工具契约和停止条件约束**。

## 先问：这件事真的需要 Agent 吗？

如果流程固定，优先写工作流；如果下一步确实依赖中间结果，才考虑 Agent。

| 任务 | 更合适的方式 | 原因 |
|:--|:--|:--|
| 上传文档 → 解析 → 建索引 | 工作流 | 步骤固定，失败点明确 |
| 查询订单状态 | 普通 API / 工作流 | 参数和权限确定 |
| 根据用户目标选择“查文档、算数、建待办” | Agent | 工具选择依赖问题语义 |
| 处理退款 | 工作流 + 人工确认 | 有明确风险与副作用 |

把工作流包装成 Agent，不会让它更智能，只会让调试路径变长。Agent 最适合处理“目标明确、路径不确定、工具集合有限”的任务。

## 一个典型故障：它为什么一直循环？

假设用户说“整理上周客户投诉并生成待办”。Agent 可以使用 `search_tickets`、`summarize`、`create_todo` 三个工具。

常见 trace 如下：

```text
1. search_tickets(query="上周客户投诉") -> 返回 0 条
2. search_tickets(query="上周客户投诉") -> 返回 0 条
3. search_tickets(query="上周客户投诉") -> 返回 0 条
...
```

模型不是故意浪费钱。它只看到“任务还没完成”，却没有被告知“相同查询没有新信息、应停止并说明原因”。修复不应靠一句“不要循环”，而应由程序维护状态：

```python
MAX_STEPS = 6

state = {
    "goal": user_goal,
    "steps": [],
    "tool_calls": [],
    "completed": False,
}

for step in range(MAX_STEPS):
    decision = decide_next_step(state)
    if decision.type == "final":
        state["completed"] = True
        break
    result = execute_tool_with_guardrails(decision)
    state["steps"].append({"decision": decision, "result": result})
else:
    state["stop_reason"] = "max_steps_reached"
```

程序必须拥有最后的停止权。除了最大步数，还应限制相同工具 + 相同参数的重复次数、单次任务预算和总耗时。

## 工具定义是 Agent 的真实能力边界

一个含糊的工具描述会诱导错误调用：

```text
search_database：搜索数据库
```

一个好的工具契约要写清：它做什么、不做什么、参数类型、返回结构、错误语义和权限范围。

```text
search_tickets
作用：查询当前用户有权限查看的客服工单；只读。
输入：query（必填，1~100 字），from_date，to_date。
输出：工单 ID、标题、创建时间、摘要；最多 20 条。
失败：无权限、参数非法、服务超时。
限制：不能查询其他租户；不能修改工单。
```

模型调用工具前是“计划”；真正执行前还要由程序验证：

```text
模型工具参数
  -> Schema 校验
  -> 当前用户鉴权
  -> 限流 / 超时 / 幂等校验
  -> 工具执行
  -> 标准化结果或错误
  -> 回写 Agent 状态
```

永远不要因为模型输出了 `delete_user` 就直接执行。涉及写入、发送、支付、删除、外部发布的工具，必须显式分级并设计确认环节。

## 记忆不是“把所有对话都塞回去”

Agent 常被要求“有记忆”，但记忆至少分三种：

| 类型 | 存什么 | 生命周期 |
|:--|:--|:--|
| 任务状态 | 当前目标、已调用工具、失败次数 | 当前任务 |
| 会话摘要 | 用户偏好、已确认的上下文 | 当前会话或有限时间 |
| 业务事实 | 经授权的文档、订单、配置 | 由业务数据源管理 |

任务状态应是结构化数据，而不是模型自己回忆。业务事实应从数据库或 RAG 检索，不应因为用户在上一轮说过一句话就当作永久真相。把这些混在一长串聊天历史中，会导致成本、隐私和错误一起增长。

## Trace 是 Agent 的调试器

Agent 出错时，只看最终回答几乎没有用。至少记录：

```text
run_id
goal
step_index
模型决策摘要
工具名与参数
工具结果 / 错误
耗时、Token、成本
停止原因
人工确认结果（如有）
```

一个健康的 trace 应能让你回答：它为什么选了这个工具？工具返回什么？为什么继续而没有停止？错误是模型决策、工具参数、权限还是下游服务造成的？

不要把用户隐私、完整 Prompt 和密钥原样写入日志；要做脱敏、访问控制和保留期限管理。

## MCP 放在系统中的位置

MCP 可以理解为“让模型客户端以统一方式发现和调用外部能力的协议”。它有助于接入工具，但不会替你解决工具权限、业务确认、失败重试和审计问题。

接入任何 MCP 工具前都应问：

1. 这个服务能读取或写入什么数据？
2. 用户是否明确授权本次动作？
3. 工具返回是否可信、是否需要二次校验？
4. 若工具不可用，Agent 应重试、换路径还是停止？

协议统一了接口，不会自动统一风险控制。

## 本篇练习：做一个“知道何时停下”的 Agent

实现一个只读的资料助手，工具仅限 `search_docs` 和 `calculator`。验收标准：

- 每次任务最多 4 步；
- 相同工具参数连续失败两次后停止；
- 无资料时输出“未找到证据”，而不是继续搜索；
- 每次工具调用都有 `run_id` 与结构化 trace；
- 不提供任何带写入副作用的工具。

再人为制造两个故障：工具超时、工具返回空结果。确认你能从 trace 定位问题，并能向用户给出诚实的失败说明。下一篇将处理另一个常被忽略的问题：当 Demo 开始有人用，如何评测、观测成本、保证安全并稳定上线。
