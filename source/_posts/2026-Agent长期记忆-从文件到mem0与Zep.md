模型没有记忆，会话历史就是它的记忆——关掉窗口就归零。所谓"长期记忆"，全是外部系统在会话开始时把相关信息重新塞进上下文。方案从简到繁差着数量级的工程成本，先搞清楚你到底需要哪一层。

## 三个层次的需求

```text
第 1 层  会话内      天然具备，就是对话历史
第 2 层  跨会话      同一用户/项目，下次还记得（本篇重点）
第 3 层  跨用户      团队知识库，本质是 RAG（已有专篇）
```

很多"我需要记忆系统"的需求，其实是第 1 层没做好（忘了压缩历史）或第 3 层没做对（知识库检索质量差）。先排除这两种。

## 方案一：文件式记忆（Claude Code 的答案）

Claude Code 的自动记忆系统是这层的教科书实现：**记忆就是一个 Markdown 文件，每次会话开始注入**。

```text
~/.claude/projects/<项目>/MEMORY.md   ← 模型自己写的笔记
~/.claude/CLAUDE.md                    ← 你写的常驻约定
```

工作机制：你在对话中纠正过它几次（"这个博客用 pnpm 不用 npm"），模型把这些教训写成一条条记忆文件；下次会话，摘要常驻注入，需要细节时按需读取单条文件。

值得学的三个设计：

1. **记忆是文本**，人可读可改可版本化，出问题能直接编辑；
2. **渐进加载**，先注入每条记忆的摘要，命中才读全文——又是上下文经济学；
3. **记录"为什么"**，不只是事实："用户偏好 pnpm"不如"项目用 pnpm-workspace，npm 会装出两套依赖"。

个人 Agent 和单人工作流，这一层基本够用，没有运维成本。

## 方案二：mem0——抽取式记忆

产品化的聊天 Agent（客服、陪伴类应用）面对的是海量用户对话，做法变成两阶段：

```text
对话结束 → LLM 从中抽取候选事实（"用户养了一只猫"）
        → 与已有记忆比对：新增 / 更新 / 冲突 / 无效
        → 存入向量库
下次对话 → 检索相关记忆 → 注入 system prompt
```

```python
from mem0 import Memory

m = Memory()
m.add("我家猫叫年糕，最近在治疗猫癣", user_id="alice")
# 下次对话时
related = m.search("宠物的注意事项", user_id="alice")
```

优点是全自动、按用户隔离；代价是每次抽取都要调 LLM（成本），抽取质量受模型能力影响，且简单的向量检索处理不好"**时效**"——"年糕在治疗猫癣"是一个状态，病好了之后它就该过期。

## 方案三：Zep——带时间线的知识图谱

Zep 把记忆组织成时间感知的知识图谱：每条事实带有效区间，支持"截至上周用户的地址还是 A，之后改成了 B"这类查询。它是三家里工程最重的，适合对记忆准确性和可解释性要求高的产品（如长期陪伴、医疗健康类助手），并且同样需要评估体系来证明它比"摘要+检索"基线更好。

## 选型：先做基线，再上系统

一个容易踩的坑是跳过基线直接上记忆框架。基线是：

```python
# 每次会话结束
summary = llm("把本次对话里关于用户偏好的内容总结成 20 条以内的事实清单")
# 下次会话
prompt = system_note + summary + 本次对话
```

几百行代码以内。然后固定一组"记忆测试题"（过一周回来问模型"我的猫怎么样了"这类），量化命中率、过期率，**基线不够好再上 mem0 / Zep**，并证明提升。

## 记忆最难的部分：遗忘

错误记忆比没有记忆更糟——模型会理直气壮地用三个月前的过期事实回答你。任何方案都要回答：

- 冲突时新事实如何覆盖旧事实；
- 被用户纠正的记忆如何删除；
- 如何防止某次对话里的错误结论被固化为长期记忆（一个做法：只在会话结束时批量抽取，抽取前让人或规则过一道）。
