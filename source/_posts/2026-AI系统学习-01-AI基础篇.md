很多人学习 AI 应用开发时，第一件事是装 LangChain、搭聊天页面、接一个最强的模型。

我更建议反过来：**先写一次最朴素的模型调用，然后亲手让它失败一次。**

因为真实工作里最棘手的事不是“模型能不能回答”，而是：它为什么这次回答对、下次又答错；错的是模型、资料、Prompt，还是我们自己的程序。

这篇不讲训练原理，也不急着引入框架。目标只有一个：做出一条你能看懂、能复现、能排查的最小 AI 链路。

## 从一个看似正确的回答开始

假设你正在做团队文档助手，先拿一个最常见的需求试水：

> 根据员工手册，回答「报销申请需要在什么时候提交？」

最初代码可能只有这样：

```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="YOUR_MODEL",
    messages=[
        {"role": "system", "content": "你是公司的行政助手。"},
        {"role": "user", "content": "报销申请需要在什么时候提交？"},
    ],
    temperature=0.7,
)

print(response.choices[0].message.content)
```

它很可能给出一段语气笃定、格式也不错的回答，例如“请在当月月底前提交”。问题是：**你的代码根本没有给它员工手册。**

这不是模型“偶尔不准”，而是系统设计出了一个无法证明正确性的回答。模型只是根据训练中常见的报销规则，生成了一个听起来合理的句子。

这就是 AI 应用的第一条工程原则：

> 语言通顺不是正确性；没有事实来源的业务回答，默认不可信。

## 先把问题拆开：模型到底看到了什么

一次模型调用可以粗略看成：

```text
系统指令 + 用户问题 + 历史消息 + 检索资料 + 工具结果
                    ↓
                模型生成
                    ↓
          校验 / 记录 / 返回给用户
```

模型并不会自动读取数据库、公司 Wiki、昨天的聊天记录或你的业务规则。它只能使用**本次请求放进上下文的内容**。

因此，同一个问题的错误，至少有四种来源：

| 现象 | 常见原因 | 第一排查点 |
|:--|:--|:--|
| 回答了不存在的制度 | 没有资料或资料没召回 | 输入上下文、检索结果 |
| 回答不符合格式 | 指令含糊、输出随机性高 | Prompt、temperature、Schema |
| 回答忽略刚说过的信息 | 历史消息没传或被截断 | 消息列表、Token 预算 |
| 同一问题偶尔好偶尔坏 | Prompt 边界不清、没有评测 | 固定样例与输出记录 |

不要一看到错误就说“模型幻觉了”。这句话没有帮助。更有用的问法是：**这一轮请求里，模型实际收到了哪些信息？**

## 做一个可审计的最小调用

先不用任何 Agent 或编排框架。把输入、参数、输出和耗时都留下来：

```python
import json
import time
from openai import OpenAI

client = OpenAI()

SYSTEM_PROMPT = """你是公司制度问答助手。
只能根据已提供的资料回答。
资料中没有答案时，明确回答“根据当前资料无法确认”，不要猜测。
返回 JSON：{"answer": "...", "has_evidence": true}。
"""

def ask(question: str, policy: str) -> dict:
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": f"资料：\n{policy}\n\n问题：{question}"},
    ]

    started_at = time.perf_counter()
    response = client.chat.completions.create(
        model="YOUR_MODEL",
        messages=messages,
        temperature=0,
        response_format={"type": "json_object"},
    )
    latency_ms = round((time.perf_counter() - started_at) * 1000)
    result = json.loads(response.choices[0].message.content)

    print(json.dumps({
        "question": question,
        "latency_ms": latency_ms,
        "model": "YOUR_MODEL",
        "result": result,
    }, ensure_ascii=False))
    return result
```

准备两段故意很短的资料：

```text
报销制度（2026-01）：
员工应在费用发生后的 30 个自然日内提交报销申请。
超过期限需要部门负责人审批。
```

然后连续问两个问题：

```python
policy = "员工应在费用发生后的 30 个自然日内提交报销申请。超过期限需要部门负责人审批。"

ask("报销申请最晚什么时候提交？", policy)
ask("出差机票必须坐哪家航空公司？", policy)
```

第一个问题应该能回答“费用发生后 30 个自然日内”。第二个问题理想情况下不应该编出航空公司，而应返回“根据当前资料无法确认”。

这两个问题一起才构成一次有效测试：它既验证“知道时能回答”，也验证“不知道时会拒答”。只测试答对的问题，会让你误以为系统很可靠。

## Token 与上下文：不是把资料塞得越多越好

刚接触大模型时，很容易把所有历史消息和所有文档都放进 Prompt。这通常会带来三个后果：

1. 成本升高，响应变慢；
2. 关键规则被长文本淹没；
3. 超过上下文限制后，早期信息被截断或丢失。

可以把上下文理解成一次考试时允许带进考场的资料。资料越多，不代表越容易找到正确答案；真正重要的是“这道题需要的那一页是否在手边，而且是否足够清晰”。

因此，后续 RAG 要解决的并不只是“向量检索”，而是一个更基础的问题：**在有限上下文中，为当前问题挑出可靠、相关、最新的证据。**

在还没引入 RAG 前，也应该养成两个习惯：

- 给每段资料加版本和来源，例如 `报销制度（2026-01）`；
- 记录每次实际传入模型的文本，而不只记录用户问题。

否则当用户说“你昨天明明说可以，今天怎么不行”，你没有任何东西可以复盘。

## temperature 不是“聪明程度”旋钮

很多教程把 temperature 解释成“创造力”。这个说法不算错，但在工程里不够具体。

它更像是输出采样的随机程度：值越高，措辞和候选答案的变化通常越大；值越低，同样输入更容易稳定复现。它不会让模型凭空知道更多事实，也不会自动消除幻觉。

一个简单的选择原则：

| 任务 | 建议 | 原因 |
|:--|:--|:--|
| 制度问答、信息抽取、JSON 输出 | 低随机性，例如 `0` | 需要稳定、便于回归测试 |
| 标题、文案、头脑风暴 | 中等随机性 | 需要多个不同表达 |
| 事实不明确的业务问答 | 不靠调 temperature 解决 | 应补资料、引用和拒答规则 |

把 temperature 调到 0 后，错误答案可能会变得**稳定地错误**。这恰好能帮助我们调试，但不能替代事实校验。

## 幻觉不是一个需要“消灭”的功能，而是一种要管理的风险

对业务系统而言，模型的风险可以分三层处理：

```text
生成前：只提供可信资料，限定任务和权限
生成中：要求基于资料回答，使用结构化输出
生成后：校验字段、展示来源、记录日志、回归评测
```

以刚才的制度问答为例，最小的防线是：

1. Prompt 规定资料不足时必须拒答；
2. 输出中强制给出 `has_evidence`；
3. 程序检查 `has_evidence=false` 时，不显示成确定结论；
4. 以后接入 RAG 时，要求返回引用片段和文档版本。

注意这里的分工：模型负责语言理解与生成；程序负责权限、数据来源、字段校验和最终业务动作。不要把“是否允许报销”“是否可以删除文件”完全交给一句自然语言回答。

## 从 Demo 到系统，至少补上这四样东西

一个聊天框能跑，不等于一个 AI 应用可维护。最小生产意识可以从下面四项开始：

### 1. 可追踪的日志

每次请求至少记录：

```text
request_id、时间、模型、Prompt 版本、输入长度、检索片段 ID、耗时、输出、错误类型
```

日志不是为了“多打一点 print”。它用于回答具体问题：某次错误是否只发生在某个 Prompt 版本？是否只发生在某类文档？是不是超时后走了降级模型？

### 2. 固定的小评测集

先用 CSV 或 Markdown 就够了：

| 问题 | 期望事实 | 是否应拒答 | 实际结果 | 错误类型 |
|:--|:--|:--:|:--|:--|
| 报销最晚何时提交？ | 30 个自然日 | 否 |  |  |
| 指定航司吗？ | 无资料 | 是 |  |  |
| 超期怎么办？ | 负责人审批 | 否 |  |  |

每次改 Prompt、换模型、调整检索都重新跑一遍。没有固定题目，就无法知道优化是真进步，还是刚好换了一个顺眼的回答。

### 3. 明确的失败输出

“不知道”不是失败。编造一个答案才是。

把以下输出当作产品能力设计：资料不足、权限不足、工具超时、格式解析失败、用户问题不清晰。用户得到明确边界，开发者也得到可统计的错误类型。

### 4. 可替换的模型层

业务代码不要到处散落模型调用。至少封装成一个客户端或服务层，让模型名、超时、重试、成本记录和降级策略在一个位置管理。这样未来更换提供方或模型版本时，不会把业务逻辑一起改坏。

## 这篇练习：故意制造三个失败

不要只做“成功调用”。请完成下面三个实验，并把结果写进 `bad_cases.md`：

1. **无资料回答**：删除制度文本，观察模型会不会猜；然后补上“资料不足时拒答”的规则，比较变化。
2. **冲突资料**：同时给出两个不同版本的截止日期，观察模型如何处理；再加入“以版本号最新者为准”的明确规则。
3. **格式错误**：去掉 JSON 约束，连续调用多次；再开启结构化输出，记录解析成功率。

每个 bad case 只写四行就够：

```text
问题：
实际输入：
错误表现：
修复方式与验证结果：
```

这些记录以后会成为你写项目 README、排查线上问题、回答面试追问时最有价值的材料。

## 学完这篇，应该带走什么

如果你只记住一句话，请记住：**AI 应用不是“把问题交给模型”，而是为模型提供证据、边界和可验证的输出。**

下一篇会继续把这条链路向前推进：如何设计 Prompt，让模型输出稳定的结构化数据，并可靠地调用程序工具。

在进入下一篇前，确认你已经做到：

- 能打印并解释一次请求里的完整消息列表；
- 能区分“模型没有资料”和“模型理解错了”；
- 有至少 3 条固定测试问题，其中包含一条应拒答的问题；
- 能让程序而不是模型决定格式校验和业务权限；
- 写下过至少一个真实 bad case。
