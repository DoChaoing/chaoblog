AI 学习的第一步，不是急着学框架，而是先理解大模型应用的基本边界。很多 AI 项目失败，并不是因为模型不够强，而是开发者没有处理好输入、上下文、事实来源、评测和工程约束。

## LLM 是什么

LLM 可以理解成一个基于上下文预测和生成文本的模型。它擅长语言理解、总结、改写、推理、代码辅助和知识整合，但它不是数据库，也不是绝对可靠的事实系统。

你需要先记住三句话：

- 模型只能基于当前上下文回答；
- 模型可能生成看似合理但并不真实的内容；
- AI 应用的可靠性来自检索、约束、评测和工程设计。

## Token 与上下文

Token 是模型处理文本的基本单位。上下文窗口决定模型一次能看到多少内容。开发时常见的问题包括：

| 问题 | 影响 |
|:--|:--|
| 输入太长 | 重要内容被截断，成本升高 |
| 上下文混乱 | 模型抓不到重点 |
| 历史对话太多 | 回答偏离当前任务 |
| 资料缺失 | 模型容易猜测或编造 |

所以 AI 应用开发不是简单把所有内容塞给模型，而是要选择和组织上下文。

## 模型能力边界

模型擅长：

- 文本总结；
- 分类和抽取；
- 生成初稿；
- 解释代码；
- 方案拆解；
- 多轮对话。

模型不擅长：

- 保证事实永远正确；
- 自动知道私有数据；
- 精确执行危险操作；
- 替代完整业务规则；
- 在没有评测的情况下证明效果。

## AI 应用基本链路

一个 AI 应用通常包括：

```text
用户输入
  -> Prompt 组织
  -> 知识检索或工具调用
  -> 模型生成
  -> 结构化校验
  -> 日志和评测
  -> 返回结果
```

后面的 Prompt、RAG、Agent、工程化，都是围绕这条链路展开。

## 本篇练习

完成三个小任务：

1. 调用一个模型 API，让它回答 10 个问题；
2. 记录其中 3 个回答不稳定或不准确的例子；
3. 写一段总结：这些问题是因为模型不知道事实、上下文不足，还是 Prompt 不清楚。

这一步很小，但它会帮你建立一个重要意识：AI 不是魔法，它需要工程化约束。

## 学习目标

读完这一篇，你应该能回答四个问题：

| 问题 | 合格答案应该包含 |
|:--|:--|
| LLM 到底是什么 | 语言模型、上下文预测、生成式能力、概率输出 |
| 为什么模型会胡说 | 缺少事实来源、上下文不足、训练知识过期、输出不可验证 |
| AI 应用和普通后端有什么不同 | 多了 Prompt、模型调用、检索、评测和不确定性处理 |
| 学 AI 应用开发先学什么 | 先学调用、Prompt、结构化输出，再学 RAG、Agent 和工程化 |

这篇不追求公式推导，而是建立工程视角。面试和项目里，最重要的是你能把“模型能力”拆成“可控的系统链路”。

## 大模型应用的三种形态

很多人一说 AI 应用，就只想到聊天机器人。其实应用形态至少有三类。

| 形态 | 例子 | 关键能力 |
|:--|:--|:--|
| 内容生成 | 写总结、写邮件、写代码注释 | Prompt、风格控制、输出校验 |
| 知识问答 | 企业知识库、客服问答、文档助手 | RAG、引用来源、拒答机制 |
| 任务执行 | 订票助手、数据分析助手、代码 Agent | 工具调用、状态管理、权限控制 |

学习时不要把所有东西混在一起。内容生成偏 Prompt，知识问答偏 RAG，任务执行偏 Agent。三者可以组合，但学习顺序最好从简单到复杂。

## AI 应用开发岗位要什么

多数 AI 应用开发岗位不要求你从零训练大模型，而是要求你能把大模型接入业务系统。你需要具备：

- 后端接口能力：能写 API，能处理请求、鉴权、异常；
- 数据处理能力：能清洗文档、切分文本、处理 JSON；
- 模型调用能力：能接入模型 API，能处理超时和错误；
- 检索能力：能做 Embedding、向量检索、关键词检索；
- 工程能力：能记录日志、做评测、控制成本、部署服务；
- 表达能力：能讲清楚项目架构、技术取舍和失败案例。

如果你是后端、前端或测试背景转 AI，优势不是“懂模型原理”，而是“能把模型做成可用系统”。

## 必须理解的十个基础概念

| 概念 | 怎么理解 | 项目中为什么重要 |
|:--|:--|:--|
| Token | 模型处理文本的单位 | 影响上下文长度、速度和成本 |
| Context | 模型当前能看到的信息 | 决定回答依据 |
| Temperature | 输出随机性 | 决定稳定还是发散 |
| System Prompt | 全局行为约束 | 控制模型角色和边界 |
| User Prompt | 用户当前请求 | 决定具体任务 |
| Few-shot | 给示例让模型模仿 | 提升格式稳定性 |
| Hallucination | 生成不真实内容 | 需要检索、引用和评测 |
| Embedding | 文本向量表示 | 用于语义检索 |
| Tool Calling | 模型选择工具并传参 | 让模型能执行外部动作 |
| Evaluation | 用样例判断效果 | 防止凭感觉优化 |

这些概念不用一开始钻太深，但要能用自己的话解释出来。

## 一条最小学习路径

如果你从零开始，可以按这个顺序动手：

1. 写一个脚本调用模型；
2. 给模型加 system prompt；
3. 让模型输出 JSON；
4. 用代码校验 JSON；
5. 准备 20 条测试问题；
6. 接入本地文档做 RAG；
7. 接入一个工具做 Agent；
8. 记录日志和 bad case；
9. 写 README 和架构图；
10. 准备项目讲稿。

这条路径比盲目刷题更可靠，因为每一步都有产出。

## 常见误区

| 误区 | 问题 | 更好的做法 |
|:--|:--|:--|
| 一开始就学微调 | 成本高，反馈慢，和应用开发距离远 | 先学 Prompt、RAG、评测 |
| 只看框架教程 | 换框架就不会做 | 先理解链路，再选框架 |
| 只做聊天页面 | 展示不出工程能力 | 加引用、日志、评测、部署 |
| 不记录失败案例 | 面试时讲不出深度 | 每次错误都写 bad case |
| 追求大而全 | 项目难完成 | 先做最小闭环 |

## 检查清单

学完本篇，检查自己是否能做到：

- 能解释 LLM 和搜索引擎的区别；
- 能解释 Token、上下文和成本的关系；
- 能说出模型幻觉的三个原因；
- 能画出 AI 应用的基本链路；
- 能列出 Prompt、RAG、Agent 分别解决的问题；
- 能写出自己的六周学习计划。

## 面试表达

当面试官问“你怎么理解 AI 应用开发”时，可以这样回答：

> 我理解的 AI 应用开发不是简单调用模型 API，而是把模型能力接入业务系统。完整链路包括用户输入、Prompt 组织、知识检索或工具调用、模型生成、结构化校验、日志和评测。模型本身有上下文限制和幻觉问题，所以工程上要通过 RAG、函数调用、评测集、日志和安全边界来提高可靠性。
