AI 面试最容易掉进一个误区：以为要证明自己“知道很多名词”。

但“熟悉 RAG、Agent、Prompt 工程”几乎无法区分候选人。面试官真正想判断的是：你是否做过一个不稳定的系统，如何发现问题、做出取舍、验证修复，并知道边界在哪里。

所以最有说服力的材料不是背诵稿，而是一组证据：代码仓库、评测表、trace、架构图、bad case 和你自己的判断。

## 简历不要写技术栈，要写可验证的动作

弱描述：

> 熟悉 Python、RAG、向量数据库、Agent。

它没有业务、动作、难点或结果。更好的写法：

> 独立实现制度知识库助手，完成 Markdown 解析、版本化分块、权限过滤与引用式问答；维护 35 条回归题和 4 个 bad case，通过检索版本过滤解决旧制度被误召回的问题。

这句话可被追问，也不夸大。一个项目 bullet 通常包括：

```text
场景：解决什么真实问题
动作：你实现了哪些关键模块
难点：哪里不稳定、为什么难
结果：用什么指标或证据验证
```

如果没有线上用户，也可以诚实写“本地评测集 35 条”而非虚构业务指标。可复现的证据比漂亮数字更有价值。

## 三分钟讲项目：把时间花在取舍上

一个可用的讲述顺序：

1. **背景（20 秒）**：资料分散，查询制度需要人工翻文档；
2. **目标（20 秒）**：回答必须带来源，无资料和无权限时明确拒答；
3. **架构（40 秒）**：解析分块、检索、生成、引用校验、日志与评测如何连接；
4. **难点（50 秒）**：一次具体错误，如何定位到某一层；
5. **取舍与结果（35 秒）**：为什么先选简单技术栈、如何用固定题验证；
6. **反思（15 秒）**：下一步会补什么，当前边界是什么。

不要把每个库都念一遍。面试官更希望听见这样的话：

> 我一开始只做了向量召回，版本更新后旧制度仍会出现。通过记录 chunk 的 version 和实际 top-k，我确认问题不在生成而在 metadata 缺失。后来先按生效日期过滤再 rerank，相关评测题的引用都指向最新版。代价是文档入库时必须维护版本字段。

这段回答同时体现了排障、证据、取舍和边界。

## RAG 追问，先分层再回答

| 问题 | 回答框架 |
|:--|:--|
| 为什么需要 RAG？ | 私有/新鲜知识不在模型上下文；通过检索提供证据，但不能保证自动正确 |
| 分块怎么做？ | 先按结构切，再按长度拆；标题、版本与页码进入 metadata；用评测验证 |
| top-k 如何选？ | 看期望 chunk 的召回与排序，不只看最终回答；过大增加噪声 |
| 答错怎样排查？ | 原文 → chunk → top-k → 实际 context → 引用 → 输出，逐层定位 |
| 如何降低幻觉？ | 证据约束、引用校验、资料不足拒答、固定回归题 |

避免只答“用了某某向量库、调了 top-k=5”。如果你不能说明为什么是 5、改成 8 会怎样，就承认是基于小评测集的初始选择，并说明下一步如何验证。

## Agent 追问，核心是控制而不是炫技

| 问题 | 回答框架 |
|:--|:--|
| Agent 与工作流有什么不同？ | 路径是否动态；固定流程优先工作流，减少不确定性 |
| 如何避免循环？ | 最大步数、重复调用检测、预算与超时、停止原因 |
| 工具如何安全？ | Schema、服务端鉴权、幂等、写操作确认、标准错误格式 |
| trace 有什么用？ | 重建每一步决策、工具参数、结果、耗时和停止原因 |
| MCP 是什么？ | 工具接入协议，不替代权限、审计和业务风险控制 |

如果没有实际做过多 Agent，不必伪装。把一个单 Agent 的失败 trace 讲清楚，通常比泛泛谈“协作规划”更可信。

## 系统设计题：先澄清，再分层，再谈风险

题目：设计企业知识库助手。不要直接画向量数据库。可以按以下顺序：

```text
1. 澄清目标：谁使用、什么文档、是否需要引用、权限如何定义
2. 输入层：登录态、问题、会话、限流
3. 数据层：解析、版本、metadata、索引更新
4. 检索层：权限过滤、召回、rerank、无结果策略
5. 生成层：证据 Prompt、结构化输出、引用校验
6. 工程层：日志、评测、缓存、成本、超时和降级
7. 风险层：越权、注入、过期资料、隐私、审计
```

系统设计没有唯一正确图。重点是每一个组件都能回答“它解决什么问题”“失败时怎样处理”“如何验证它有效”。

## 面试材料，不要等到前一天才整理

给自己的项目准备一个证据包：

- 一页架构图：标出数据流和权限边界；
- 一份 README：能启动、能跑评测、写清限制；
- 一张评测表：成功题、拒答题、权限题和结果；
- 三个 bad case：包含定位过程和修复验证；
- 两段项目讲稿：1 分钟简介与 3 分钟深讲；
- 一个可演示的稳定版本：即使外部服务不可用，也能说明降级行为。

这些材料的作用不只是面试。它们也是你持续维护项目的文档。

## 最后一条建议：诚实地说出边界

遇到没有做过的问题，最差的做法是硬编，最好的做法是展示思考框架：

> 这个方案我还没有在线上完整实践。我会先确认数据权限和成功标准，再拆成检索质量、生成引用、延迟成本和安全边界；先用小评测集验证，再逐步扩大范围。

这不是示弱，而是工程师面对不确定系统时应有的工作方式。到这里，整条学习路线真正要训练的能力也很清楚了：不是让模型看起来无所不能，而是把它变成有证据、有边界、可验证的产品能力。
